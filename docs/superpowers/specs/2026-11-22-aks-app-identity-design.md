# Phase 4 slice 2 application identity

**Status:** Draft for review. Each database request has one owning app. The selected catalog offerings are Azure HorizonDB and PostgreSQL on AKS with CloudNativePG.

The managed identity proof targets Azure HorizonDB. The sample app uses its own workload identity to query a private database on managed AKS. A second app in the same team must be able to get its own token and reach the database endpoint, then be denied by PostgreSQL. The existing cross-team, alternate ServiceAccount and cleanup checks in [ADR-0008](../../adr/0008-application-workload-identity.md) still apply. The [Phase 4 tracker](../../adr/README.md#phase-4-exit-criteria-tracker-d-087) defines the managed network gate.

## Database catalog

Backstage will offer two choices for a service database. The request opens a Git PR, and the platform validates the offering and ownership when it reconciles the request. Database security applies to requests submitted directly through Git as well as requests generated by Backstage.

The single-subscription sandbox uses the installer-supplied Terraform `subscription_id`. [ADR-0013](../../adr/0013-subscription-placement-and-vending.md) defines the source of truth for deployment metadata and the future multi-subscription placement contract.

| Offering | Evidence required before enabling requests |
| --- | --- |
| Azure HorizonDB | A supported provisioning and teardown path in the target region, private connectivity with TLS, an Entra workload identity with a least-privilege database role, and a tested restore. |
| PostgreSQL on AKS with CloudNativePG | A supported AKS and operator version pairing, operator deployment on the workload cluster, app-scoped authentication, private connectivity with TLS, tenant isolation, failover, and a tested off-cluster restore. |

Azure Database for PostgreSQL Flexible Server is the existing implementation in the repository. The proposed change to the managed backend needs to be reconciled with D-082 and D-086 after design review. The existing kind path provides local development coverage. Its operator and password flow alone are insufficient evidence for the AKS catalog offering.

Qualify both offerings on the existing split AKS sandbox using its Terraform version override for Kubernetes 1.36, subject to regional preflight. CloudNativePG 1.30.x lists Kubernetes 1.36 as supported and 1.37 as tested outside its supported range. Recheck that matrix before changing the sandbox default or promoting another pairing.

## Follow-on catalog offerings for storage

Use the same Backstage-to-Git workflow for service-owned object storage and shared file storage. Present the protocol and supported tiers for each offering. Enforce ownership and backend authorization when the request is reconciled. Require private access, a cross-tenant denial test, and a recovery test before enabling requests.

| Capability | Managed offering | Workload-cluster candidate |
| --- | --- | --- |
| Object storage | Azure Blob Storage in an approved storage account, with supported online access tiers and archive as a lifecycle option | S3-compatible buckets through Rook-managed Ceph Object Gateway |
| Shared file storage | Azure Files shares, with supported SMB or NFS and HDD or SSD combinations | CephFS volumes through Rook and Ceph CSI |

Azure Blob and S3 use different client interfaces. The request must identify the selected protocol. The public MinIO Operator repository is archived. A MinIO offering would require a maintained, supported distribution to be identified and reviewed.

## Ownership and lifecycle

Add a typed application reference to the PostgreSQL request. The reference is the app name in the same team and environment. The tenant namespace supplies the team, environment and workload group. Require the reference for Azure and preserve the existing kind request format and brokered credentials. Once set, the reference is immutable. A different app needs a new request and an explicit data migration.

The AppIdentity XR uses its name as the app name. Before provisioning runtime database access, the platform must verify the referenced request is in the same tenant namespace and names this app. An absent or mismatched reference yields no grant and an actionable reconcile status. A platform-owned bootstrap identity provisions the HorizonDB runtime role with only the app's required database privileges. The CloudNativePG offering must enforce the same ownership and runtime privilege boundary. This design assumes trusted reviewers for the team deploy repository, which can change both app declarations and database requests.

Use the control-plane EnvironmentConfig and Terraform's workload cluster output to resolve the issuers in the tenant's workload group. Derive the ServiceAccount subject from the tenant namespace and app name. The identity request cannot supply an issuer, subject, tenant, resource group or a raw Azure grant. If placement or owner inputs are missing, report them explicitly. Hold the last valid set of reconciled resources on a transient lookup failure. A confirmed removal from placement or from the app's declared dependencies must remove the corresponding credential or grant.

Build on the existing per-tenant ESO path for the app's client and tenant IDs. Names for app identity metadata and database connection metadata must be disjoint even when their request names match. The cloud chart profile projects a token for the app ServiceAccount and mounts it only in the app containers that need it. Keep managed and BYO app-facing renders equivalent for the same platform inputs. On kind, the local AppIdentity composition reports the existing password-based deviation.

Document and test the deletion order before enabling the Azure path. Drop the database grant before removing its identity or database, and verify that repeated cleanup handles resources already absent. The AKS teardown must drain AppIdentity XRs as well as PostgreSQL XRs before destroying Terraform foundations.

## Managed network path

Verify the HorizonDB private connectivity and DNS requirements before choosing the network configuration. Scope database egress to the approved database destination and PostgreSQL port. Use the baseline HTTPS egress in D-086 for token exchange. Add the managed Gateway profile and supply the approved app domain through platform values. Run the same Gateway API contract suite against the managed workload cluster, with the platform's ingress configuration supplied by the environment.

## Evidence required

| Check | Passing evidence |
| --- | --- |
| Offline composition cases | Valid owner renders one grant and only issuers in the selected group. Missing owner, wrong owner and missing placement render no new grants. A transient lookup failure preserves active resources. Confirmed removal prunes the corresponding grant or credential. |
| Chart and local behavior | Managed and BYO renders agree for equivalent inputs. Stable and canary use the intended ServiceAccount. Existing kind app requests and the password-based database journey still work. |
| Azure allow | The owning app exchanges its projected token and completes a query over the private database path. |
| Runtime privilege deny | The owning app can run its application query. An administrative operation that requires a role it was never granted is denied. |
| Same-team wrong-app deny | A second app obtains a token as itself. With the same network reachability and database endpoint, PostgreSQL rejects the login. |
| Wrong-ServiceAccount deny | A different ServiceAccount in the owning namespace attempts to exchange its projected token for the owner's identity. Entra refuses the exchange, before the database is contacted. |
| Cross-team deny | Cross-team access fails. Record separately whether the network blocks the path or the connected database rejects the identity. |
| Lifecycle | Removing the app's requests removes its grant, federated credentials and identity. A teardown query against Azure verifies that the environment leaves no resources behind. |
| Managed ingress and networking | The Gateway API contract suite passes on managed AKS and the app responds on its approved HTTPS host. |
| Workload-cluster database | Cross-tenant requests are denied, a primary failover succeeds, and the platform restores a backup to a fresh cluster and verifies a query. |

The live run depends on the cloud preflight and the owner's confirmation of the subscription, region, permissions, quota, budget, timeout and teardown owner. Azure provisioning is a separate operation after the design and implementation are ready.
